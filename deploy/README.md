# Scripted deployments

Use a trusted deploy host to run one project and environment at a time. Keep its registry at `~/.config/harness/deploy.json` with mode 0600. The deployment operator owns the registry, deploy script checkout, state directory and broker executable. Verify the runner's OCI digest before adding it to the registry. Local qualification can use Docker's content-addressed image ID. Keep the installed broker's target and signer policy independent of the reviewed project files.

```bash
bash deploy/build-image.sh
harness deploy prepare fluora --ref "$SOURCE_SHA"
harness deploy fluora staging --release "$RELEASE_ID" --plan
harness deploy fluora staging --release "$RELEASE_ID"
harness deploy status "$STAGING_RUN" --scope
harness deploy signoff "$STAGING_RUN" --receipt "$SIGNED_REVIEW"
harness deploy fluora preprod --release "$RELEASE_ID" --from "$STAGING_RUN"
harness deploy status "$PREPROD_RUN"
harness deploy rollback fluora staging --run "$STAGING_RUN" --plan
harness deploy rollback fluora staging --run "$STAGING_RUN"
```

The example registry is an enrollment template. Set absolute paths and pinned public keys from the deployment host. Populate each environment's expected bindings, migration digests, secret names and feature flags from reviewed inventory. Each allowed cross-environment difference has a named field and rationale. Live values must match the corresponding reviewed profile. The report shows provider release identities and missing environment coverage. An environment is eligible for promotion only once its immediate predecessor is routed, verified and signed off for the exact same release. A reviewer includes the digest from `status --scope` in a signed canonical JSON payload. For a design of the release identity, read the [deployment specification](../specification/features/planned/container-deploy-command.md).

`prepare` verifies source reachability against the registered remote ref and builds a Git archive in Docker without provider credentials. A release ID binds the source, script and registry manifest, image ID and artifact SHA-256. A plan reads provider inventory without invoking the write interface. A failed or interrupted apply holds its target claim until `harness deploy resume <run>` reconciles it. Reconciliation looks up the already-submitted operation and can retry route verification and run-owned cleanup. Request a fresh approval for a distinct mutation. Rollback restores the recorded previous deployment and verifies the route. A schema or configuration transition requires a separate reviewed recovery plan.

## Broker contract

The owner-controlled executable named by `broker` accepts one operation as argv and a JSON request on stdin. Its stdout is one typed JSON receipt. The host scrubs inherited provider variables and stores only parsed evidence. Use a configured broker action and exact resource scopes. A broker implementation must own a durable one-use provider claim and a trusted deploy network that restricts egress to the provider and the approved route. Credentialed phases run the reviewed scripts in the same pinned deploy image with read-only inputs, isolated scratch and no host credentials directory or Docker socket. The token reaches only the authorized container through stdin. The broker must keep the token and provider response bodies out of stdout, logs and receipts.

| Operation   | Request and result                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `inspect`   | Input `project`, `environment`, `manifest`, `target`. Return the authenticated target, current provider version, source SHA, artifact digest when present, timestamp and filtered profile.                                                                                                                                                                                                                                               |
| `authorize` | Input `plan`. Return an Ed25519 approval payload plus the detached signature encoded as unpadded base64url. The nonce is the UUID on the plan. A registered staging authority can attest the authorized staging action. Higher environments require an attestation verified against Daniel's pinned approval issuer for this exact plan. The signature scope is the plan's canonical SHA-256 and expires within 120 seconds of issuance. |
| `apply`     | Input `plan`, `proof` and host `artifact` path or null for a rollback. Consume the grant before submitting, reacquire the exact reviewed script and artifact, recheck the target and predecessor, then execute the named mutation under the claim. Return a stable provider operation ID and verified observation.                                                                                                                       |
| `reconcile` | Input `plan`. Return `pending`, `applied` with the existing operation receipt, or `not-applied` with a fresh observation showing the prior target. Use only authoritative provider evidence for a terminal result.                                                                                                                                                                                                                       |

Canonical JSON sorts object keys by their UTF-8 bytes and preserves array order. A sign-off payload contains `kind: "signoff"`, the reviewer's registered `issuer`, the scope from status, UTC epoch millisecond `issuedAt` and `expiresAt`, and an opaque `reference`. Keep sign-off keys outside the runner and distinct from deployment approval keys. The tracker records verified receipt references before provider mutation.

## Native exact-release approvals

For synthetic qualification, the host registry may define `approvalInbox` with the exact HTTPS Hub `origin`, the pinned Google actor ID in `owner`, and a `credentials` map keyed by `project:preprod` or `project:prod`. Each entry points to an owner-only file for that dedicated runner grant. In Hub, migration `0008-deploy-approvals.sql` stores decisions and one-time claims. `HARNESS_DEPLOY_APPROVER_ID` identifies the same Google actor, and `HARNESS_DEPLOY_RUNNER_GRANTS` maps each scope to its grant's SHA-256. Use the approved credential broker to provision each grant for its exact scope.

The runner opens a five-minute request before holding the provider target claim. An allow can be collected once while the native session remains live. For this lane, the broker's `authorize` request includes the Hub `decision`. The broker signs the canonical plan digest and sets the proof's reference to `decision:<receipt UUID>`. Advance the original plan only after the runner verifies Daniel's signature, decision reference, current parity, predecessor sign-off and artifact bytes. An expired request or lost one-time response requires a new plan. Higher-environment rollback requires a recorded artifact digest in this lane.

The synthetic integration uses a disposable Hub database, fixture-only grants and a scripted provider. A live target requires separate broker enrollment and release qualification.

## Fluora Next pilot

The stage target is Pages project `fluora-next-stage` on its canonical `main` route, with D1 `fluora-stage` and staging R2. Production is a distinct Pages project, `fluora-next`, with its own D1 and R2. Fluora Next's current release manual declares no preprod. The pilot scripts can inspect prod but only mutate the dedicated stage Pages project. The old Fluora deployment branches and projects are separate.

The host verifies the private Conversation Engine pin against its trusted remote branch and supplies a shallow copy of that commit. Docker receives source only. The build runs Fluora's locked dependency install, unit suite and web build. The deploy script hashes the same artifact inside the runner, stamps its build identity onto the routed site and pins the staging binding file. Inspection queries only configuration and the D1 schema and migration ledger. Cloudflare D1 reports migration names, so inspection joins these names to the reviewed source-file digests and verifies the registered live schema fingerprint. The candidate migration manifest must match the applied ledger for every migration the release requires. The pilot performs no D1 writes or database restoration. Signed-out smoke checks the release marker, sign-in, auth config, protected routes, the font and adventure art. Cleanup removes run-owned ephemeral resources and retains the protected release artifacts.

This checkout contains the operator-side broker contract and the Fluora scripts. The host needs a configured Cloudflare broker action with the exact staging project permission and read-only inventory for the declared environments before executing the pilot. The current primary enrollment does not offer that action. No production deploy approval is recorded. See [Cloudflare Pages rollback](https://developers.cloudflare.com/pages/configuration/rollbacks/) and [Google Cloud CLI versioned archives](https://docs.cloud.google.com/sdk/docs/downloads-versioned-archives).
