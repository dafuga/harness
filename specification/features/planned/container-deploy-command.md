# Harness deployments in Docker

Daniel approved implementation and the Fluora Next staging pilot on Tracker item `56x4kx` on 21 November at 20:45 UTC. Fluora is the first pilot, followed by Harness Hub and BuildFlexity. Higher environment writes require separate exact-release approvals. This work can proceed independently of the Tracker CLI cutover in `m8fkcj`.

## Command and release identity

| Proposed command                                          | Behavior                                                                                                                                                                                                                                                                       |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `harness deploy <project> <env> --plan --ref <sha>`       | Resolve an authorized source revision for staging, or use `--release <id>` to inspect a promotion of an existing release. Read current versions and expected parity, show the operation and its gate requirements, and record a plan ID. Planning performs no provider writes. |
| `harness deploy <project> staging --ref <sha>`            | Build once from the pinned source, test the release, store the immutable artifacts and deploy staging. Produce a run and receipt for sign-off.                                                                                                                                 |
| `harness deploy <project> <preprod\|prod> --release <id>` | Take the recorded artifact from the preceding environment, check parity and gates, obtain Daniel's approval for this attempt, then deploy the one named target.                                                                                                                |
| `harness deploy status <run-id>`                          | Show phase, redacted parity differences, sign-off and approval references, observed provider version, smoke result, rollback target and cleanup state.                                                                                                                         |
| `harness deploy signoff <run-id>`                         | An authenticated authorized reviewer signs the successful deployment, its verification evidence and its immutable release identity.                                                                                                                                            |
| `harness deploy rollback <project> <env> --run <id>`      | Plan and execute the recorded restoration for that run using the same guarded workflow.                                                                                                                                                                                        |

Expose machine-readable output. Use the project's declared environment names and an explicit alias map, such as `prod` for a provider slot called `production`. Each invocation acts on one environment. Capture a release ID over the source SHA, artifact digests, tested scripts/config revision, build toolchain and migration digests. The build input includes the lockfiles and pinned image. A release with several deployable components records each digest. Preprod and prod consume the exact staging artifacts. Environment-specific bindings and public configuration are separately identified overlays with their own digests. A project that cannot consume the same artifacts across stages is ineligible until its packaging path is adapted and proven.

## Execution and project configuration

Use the container lifecycle developed in `zfep7c`, including explicit local runtime selection, bounded resources, exact argument passing, exit and cancellation handling, ownership labels and task-scoped cleanup. Start with plain Docker, a local pinned image and uncontended fixtures. Reuse low-level lifecycle code from draft #163. Deployment does not depend on the interactive provider, its sandbox or local `sbx` availability. Add deployment-specific mounts, network policy and approval checks above the lifecycle layer. Measure startup and script time, CPU, peak RAM and disk for the pilot before adopting it elsewhere.

Maintain one reusable OCI deploy image with pinned Wrangler, Google Cloud CLI, Node, Bun, a shell, Git, CA certificates and minimal JSON, archive and HTTP tools. Publish its manifest digest and supported architectures. Check the image and tool versions before execution. The runner invokes only reviewed project scripts. The image runs nonroot with a read-only root filesystem, declared writable scratch and artifact mounts, and no Docker socket or host home mount. Build without write credentials. The deploy phase receives egress only to the configured provider and smoke endpoints. Track image and dependency updates by digest and test them against both project adapters before adoption.

Proposed `harness.deploy.json` is versioned at the source revision. It declares the project, trusted repository and source branches, environment-to-provider resource mappings, ordered stages, smoke criteria, parity profile and allowed differences, tested script paths and argv, artifacts, migrations, scopes, timeouts and rollback policy. Use the existing `harness.platforms.json` catalog as descriptive inventory. The deployment manifest supplies the enforceable contract.

| Project script | Inputs and result                                                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Build          | Pinned revision and image, lockfiles and a clean workspace. Emits immutable artifacts and a digest manifest.                         |
| Inspect        | Read-only typed inventory of live artifact/version, bindings, secret names, migrations, runtimes, flags and current rollback target. |
| Deploy         | Verified plan, exact artifacts and scoped broker access. Returns provider release IDs, before/after version and migration receipts.  |
| Smoke          | Checks the actual routed release and its health and behavior. Returns the tested revision, observations and verdict.                 |
| Rollback       | Restores the approved prior release and traffic target. Runs rollback smoke and reports data/schema compatibility.                   |
| Cleanup        | Removes only resources owned by the run after retention and rollback protection apply. Reports items removed and any residual work.  |

The host obtains short-lived, project/environment/action-scoped access exclusively through the credential broker. Inject it for the authorized phase through an approved ephemeral channel or host-side mediation, then revoke or discard it. Never store secret values in the image, source, artifact, command arguments, Tracker records or evidence. A plan uses a read-only broker binding. Before any higher-environment write, verify a durable Daniel approval and consume the corresponding execution claim. Existing direct deploy paths and credentials must be fenced at pilot adoption so they cannot bypass the gate. The plan stage does not change those paths.

## Parity and approval gates

Compare the approved desired staging, preprod and prod manifests and read back the live state at each stage. Display expected differences with a reason and show unexpected differences as blockers. Include:

- **Artifact and lineage.** Source and per-component artifact digests match the approved predecessor. After deployment, the provider and routed endpoint identify that artifact. Before deployment the current target may still be on its recorded prior release.
- **Bindings and configuration.** Compare logical binding names, types and intended scopes, including provider routing and declared environment mapping. Actual account and resource IDs can differ as required by isolation. Compare secret names and presence only. Treat approved flag and public-config differences as explicit typed entries with a reason and review record.
- **Migrations.** Compare ordered migration IDs and checksums, schema expectations and pending transitions. Allow the recorded transition from the target's current state to the signed release. Block an unexpected schema or applied migration. Record backup or restore evidence when required.
- **Versions.** Compare deployed runtimes and compatibility settings, the deploy image and tool versions, and the smoke contract. Abort when an inspection is missing, stale, scoped to the wrong environment or changed since approval.

| Target  | Requirements before mutation                                                                                                      |
| ------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Staging | Authorized source, project test results, verified target identity, expected parity and captured rollback plan.                    |
| Preprod | Staging deployed and signed off for this exact release and parity plan, then a fresh Daniel approval for this preprod deployment. |
| Prod    | Preprod deployed and signed off for this exact release and parity plan, then a fresh Daniel approval for this prod deployment.    |

Bind sign-offs to the authenticated reviewer, exact release, predecessor run, parity digest, smoke and provider evidence, time and verdict. Bind each Daniel approval to the plan digest, project, environment, action, release, attempt, predecessor sign-off, rollback scope and expiration. Use phone approval through Credential Vault where supported and verify the issued receipt against the broker. Record immutable gate and run receipts with their IDs on the project release Tracker item. Free-text Tracker notes provide context. Authorization is the verified broker and sign-off evidence. Keep Tracker recording behind the existing interface during the CLI migration. Verify the prerequisite records before granting write access.

Hold one deployment claim per project and target at a time. Reinspect immediately before mutation and reject stale or replayed approvals, changed inputs, missing predecessor, wrong approver, drift and concurrent attempts. Polling an already submitted operation resumes only by its provider ID. Any new higher-environment mutation needs a fresh approval. Persist the provider request and result so an interrupted run can reconcile before it retries.

## Smoke, rollback and cleanup

Before mutation record the previous immutable release, provider traffic target, schema compatibility and any restore snapshot. Run project smoke against the intended route after mutation, check revision and guard against redirecting to the wrong target. Verify app behavior as well as health and retain results through the project-declared observation window. Block sign-off if smoke or checkout-to-runtime lineage is unresolved.

Stop or restore on application, routing or migration failure according to the recorded policy. Automatic restoration is permitted only if covered by the exact approval and previously tested. Higher-environment rollback outside that approval needs Daniel's approval. Never blindly reverse an irreversible migration or delete shared state. Escalate with the observed release and data state when restoration is uncertain. Separate a post-smoke cleanup failure from a release failure. Hold cleanup retry with exact resource ownership and an audit receipt. Protect the previous release and its restore assets until the rollback window closes. Always remove task-owned containers and scratch, close broker access and report any residual resources. Keep the pinned shared runner image under managed retention.

## Verification and pilot order

1. **Shared runner fixtures.** Exercise actual Docker with scripts only. Prove plan has no writes, the one-artifact chain succeeds, and admissions reject missing, stale, replayed or wrong-scope approval, unsigned predecessor, changed parity, concurrent target mutation and mismatched digests. Use synthetic credentials. Cover interrupted deploy reconciliation, denied credential requests, command exit propagation, smoke-triggered restoration, cleanup-only failure and run-owned resource removal. Inspect evidence for credential disclosure.
2. **Fluora Next first.** Build the current trusted `dafuga/fluora` dev revision in the pinned image, deploy to the canonical route of the dedicated `fluora-next-stage` Pages project, exercise signed-out smoke, restore the previous stage deployment, and record provider and cleanup receipts. The current runbook declares staging and prod; a missing preprod blocks the prod gate. The stage pilot performs no D1 writes and requires scoped credential-broker support. See [the pilot runbook](../../../deploy/README.md).
3. **Harness Hub next.** Map the current manual runbook for Cloudflare Pages project `dafuga-harness` into reviewed scripts. Verify the actual target IDs and approved nonproduction topology with CoS before a live pilot. Repository sources `packages/hub/README.md` and `packages/hub/wrangler.jsonc` identify provider requirements and local placeholders. Cover D1 `DB` with ordered migration checks, R2 `CACHE`, any declared remote-host binding, secret-name inventory and compatibility settings. Smoke the routed artifact, sign-in/config readiness and one owner/member flow with a permitted fixture. Rehearse prior-version recovery and schema compatibility. Compare against the manual runbook in a disposable environment first. Staging and preprod must be defined and evidenced before the respective higher-environment gates can pass.
4. **BuildFlexity after Harness Hub.** Adapt its existing release scripts and approval topology while keeping the Google slot and rollback behavior. The repository's Google runtime workflow targets preprod and production. Confirm the full staging/test promotion path and current manual runbook with the project owner. Reuse `.github/workflows/deploy-google.yml` and `scripts/google/deploy-release.sh` and `rollback-release.sh` as the onboarding sources. Prove immutable release and slot parity, database and object-store isolation, migration or restore behavior and the PDF worker artifact when it is part of the release. Smoke public health, sign-in and a seeded PDF/render/download workflow in the permitted test environment. Verify a failed cleanup retry preserves old shared storage generations and the active and fallback release.
5. **Adoption decision.** Daniel reviews this spec first. For each pilot, accept only after its own scripted tests, independent parity and approval-gate fixtures, complete rollback and smoke, runtime and cleanup measurements, and an agreed legacy pipeline fence. The staging pilot and each later environment receive their own authorization. No candidate rollout is part of this spec task.
